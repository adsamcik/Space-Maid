# Local assistant

Open **Extensions → Local assistant → Open workflow**. Enable the assistant and choose a local GGUF instruction model, then choose a folder already included in the current scan. Optional exclusions are full paths inside that folder, one per line. Refresh the summary after changing the scope or exclusions; **Find suggestions** starts the investigation. No model is downloaded or selected automatically. Settings retain only enablement and the selected model path; questions, responses and investigations are not saved.

The main table separates **Model suggestion · verify yourself** from host policy. Select a suggestion to open its location or request **Review in Opportunities**. The model cannot establish that arbitrary personal files are disposable. Age and filenames do not establish last use or abandonment.

## Framework choice

[Microsoft.Extensions.AI](https://learn.microsoft.com/en-us/dotnet/ai/microsoft-extensions-ai) supplies a small, provider-independent .NET `IChatClient` interface. This implementation uses `Microsoft.Extensions.AI.Abstractions` 10.10.1 both at the application boundary and in the model worker. A bounded application broker validates every model command; automatic tool invocation is unnecessary because the model must never receive a host service or executable cleanup operation. [Semantic Kernel](https://learn.microsoft.com/en-us/semantic-kernel/overview/) adds orchestration that this workflow does not currently need.

The separate worker uses released `LLamaSharp` 0.27.0 with the matching `LLamaSharp.Backend.Cpu` 0.27.0 package and its [official IChatClient adapter](https://github.com/SciSharp/LLamaSharp/blob/v0.27.0/LLama/Extensions/LLamaExecutorExtensions.cs). The desktop process does not load LLamaSharp or the native inference library. There is no Ollama/HTTP fallback: an independently running model server would have its own disk/network privileges and would bypass this isolation boundary.

CPU inference accepts a supported GGUF text instruction model with an embedded chat template. Compatibility depends on the pinned native backend and template support; a model that works in a different runtime is not automatically compatible here. Unsupported models/templates produce a concise error and no suggestions. This release targets Windows x64. The worker is published self-contained during the normal host build and needs no separate .NET runtime installation. The native CPU backend also requires the Microsoft Visual C++ x64 runtime; a missing native dependency produces a repair message.

## Isolation and data access

The launcher creates a fresh [low privilege AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation) with the single, explicitly verified `registryRead` capability required for Windows native-library bootstrap. This grants access to system registry keys whose ACLs permit that capability; it does not grant user registry access generally. There are no network, file-library, device or COM capabilities. The host verifies its effective token before resuming it; the worker independently refuses unrestricted execution or any other capability before loading native inference. A Windows Job Object owns the process, limits it to one process, caps memory at 16 GiB and CPU at 80%, applies UI restrictions and kills it on closure. Worker startup is detached and hidden. It inherits only protocol pipes and a minimal environment, with diagnostics disabled and a private scratch/TEMP directory.

Only the dedicated worker runtime receives read/execute access; only the user-selected model receives read access. These are temporary non-inheriting ACL grants for a fresh sandbox SID. File and ancestor handles pin the namespace, reject reparse/cloud/offline paths and prevent runtime/model replacement during the run. Original disk data receives no grants. Disposal terminates the owned process, removes only its SID's permissions while retaining unrelated ACL changes, and deletes its private profile. Startup failure rolls back grants. There is no unrestricted retry.

The sandbox protects against an untrusted model/native worker, not a malicious trusted extension DLL or Windows/kernel exploit. Extensions continue to be trusted local application code. The selected model and packaged runtime must reside on supported local drive storage outside each other; UNC paths, alternate streams, redirects and provider placeholders are rejected. The launcher requires permission to manage the selected model's ACL, and may fail closed on storage with unsuitable permissions.

The host sends text only: the request, issued IDs, scoped names/paths, deterministic summaries and accounting/policy limits. Summary IDs use the same plain GUID strings as browsing results; all measured facts and cautions are preserved without duplicating display prose. Browsing is over the immutable scan snapshot, not live content reads. Supported model commands are `children`, filename `search`, `details`, `summary`, `propose` and `done`. Native generation constrains their JSON format, while the host independently validates every field, ID and proposal. The model cannot change the root/exclusions, submit arbitrary paths, read contents, run a shell, contact a server or invoke review/cleanup. Excluded names and global warning text are omitted from model context; warning counts and their coverage consequences remain visible.

Each investigation allows at most 12 model turns, 20 results per query/proposal, three invalid commands and 48 KiB of UTF-8 context. IPC has strict versioned frames, IDs, duplicate/unknown-field rejection and request/response caps. Native output is drained separately and bounded. The model context has 8,192 tokens and at most 1,024 output tokens per turn; the worker checks token budget before inference. A turn has a two-minute host deadline, and the overall investigation has six minutes. Cancellation, disabling the assistant, closing its workflow or replacing the scan discards unfinished results and stops the worker. Human review has no automatic model deadline.

Within the same worker, a continuation can reuse the model's processed conversation context. Reuse requires the entire prior request, the exact generated assistant reply, one new user message and an aligned native end marker/template suffix. A changed history or incompatible runtime/template state disposes that context and starts fresh. Models requiring a reset reprocess the prompt on each step. Independent `IChatClient` requests never inherit an unrelated conversation.

## Human cleanup review

An admitted proposal contains investigation items only. Model claims never create an `Opportunity`, `CleanupPlan` or deletion target. Review is a separate human-triggered host capability accepting only an owned, current evidence session and issued directory IDs. It rejects blocked items, incomplete coverage and selected folders that contain any user exclusion.

The host maps selected paths to already discovered deterministic Opportunities. Unmatched folders remain manual investigations. Matched folders go through the existing live metadata/rule, identity, build-retention and Git checks and the normal exact-path review. **Keep folders** remains the default; recycling requires explicit confirmation. The worker has exited before review is enabled. Previous unrelated selections are restored only when their captured folder identity still survives a recheck.

Summary refresh reads the existing scan and cannot repair underlying disk-scan warnings or retained metadata. Scan the selected folder separately or refresh the underlying scan first. Partial query coverage and unknown allocation remain explicit; neither model admission nor human approval bypasses host safeguards.

## Verification

Focused tests exercise the standard .NET client protocol, scoped commands, excluded-name privacy, invented IDs/actions, scan replacement, query budgets, cancellation, ownership and exclusion checks before human review. Windows tests use the actual self-contained worker to check its token, original/model/runtime access, child-process/network/environment boundaries, idle termination, redirected ancestors and ACL/profile cleanup. WPF interaction checks exercise suggestions, selection, user-triggered location/review, exclusions and disabling during a pending turn, with light/dark and compact renders.

The `registryRead` capability is a documented [LPAC bootstrap option](https://chromium.googlesource.com/chromium/src/+/show/main/docs/design/sandbox.md). Native-library loading was denied without it; granting exactly that capability allowed the native backend to reach model loading. Verification checks the original user's private registry fixture through an explicit `HKEY_USERS` path, avoiding a false pass from AppContainer HKCU redirection. Network verification requires actual socket-policy **AccessDenied**, with an active loopback listener. These observations establish the tested boundary on this Windows machine; they are not an audit of every operating-system configuration or proof that suggested user data is safe to remove.

Release packaging completed with no warnings or errors. The existing full test set passed in two runs: 326 non-desktop tests passed with two existing administrator-only skips, and the complete WPF desktop smoke passed separately. After the context-reuse correction, all 46 affected client, broker, review and native isolation checks passed with no skips, including two new continuation/formatting tests and the nine native sandbox checks. Light/dark and compact assistant renders were inspected. Real `IChatClient` inference with a local Llama3.1 GGUF succeeded inside the restricted worker; compatibility with every GGUF architecture and performance on other hardware remain unverified.

The final public `AssistantInvestigation` completed a focused request using its initially supplied evidence in 72.24 seconds: the trusted result reported two files and 6,144 logical bytes, the model returned a matching unverified note, and all three fixture files (including the excluded file) remained intact. A separate longer investigation admitted a real scoped summary and filename search, then reached the unchanged 115-second worker limit on turn three after 307.75 seconds overall; it published no final investigation. This model's rewritten EOS required context reset, so its growing CPU prompt was reprocessed. Complete multi-step performance for this 8B model remains a limitation; timeout handling discards unfinished results.
