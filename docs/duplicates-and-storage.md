# Duplicates and storage preservation

Scan a local location, then choose **More → Duplicates and storage**. **Find duplicates** compares files within that existing scan. It does not delete files, replace names or create hard links. **Inspect build file** also supports an individual cold build resource, even when it has no duplicate.

Comparison first reads live native identity, default-stream length and stream metadata. Multiple names for one `(volume, file ID)` are counted as existing aliases. Independent equal-sized files receive full SHA-256 hashing and a complete byte comparison against a stable keeper. Results describe equal default streams: extra named streams remain distinct data, and related files such as XMP are never modified. A content match does not imply that either path can be removed.

The default search page examines at most 20,000 files, reads at most 1 GiB of content and spends at most 30 seconds between bounded operations. Advanced options set the minimum size, content-read limit and exclusions. A bounded search session retains native revisions, pending size groups, hashes and completed comparisons across **Next page**, so matching files in different pages can be found. Retained keepers are revalidated before new comparisons, and no file handles stay open between pages. Cancellation retains completed work. Changing query options starts a new session. The session retains at most 50,000 file objects by default; reaching that limit reports incomplete coverage and asks for a smaller scope. Incomplete scans, inaccessible files, interrupted verification and per-page limits remain explicit. A file/pair that exceeds a whole page's content-read limit requires a larger limit; it is never declared equal from a partial hash or comparison.

Counts of redundant logical content are not guaranteed physical savings. Existing hardlinks already share an object, and separate ReFS file objects can already share extents. Allocation shown for each file is observed filesystem allocation; unrelated writes can also affect free-space measurements.

## Explicit storage actions

Each action reopens and revalidates captured volume, native file identity, creation/write/change evidence, complete contents and stream/link restrictions. Directory guards use effective list access, and file data handles exclude concurrent writes and replacement without recalling provider-backed data. Files with shared names, alternate streams, unavailable/encrypted/system storage or unsupported native metadata remain unchanged.

**Compress selected** applies standard per-file NTFS compression to a selected `.pdb`, `.obj`, `.lib`, `.rlib` or `.dll` with creation/write activity older than 14 days. It preserves the file name and identity, verifies the entire payload after compression, restores creation/access/write timestamps and reports observed allocation before and after. This is an explicit preservation action, not a claim that the file is disposable. **Undo compression** reverses the storage state after fresh inspection. Compression may reduce storage at a cost to subsequent CPU/I/O; an incompressible file may save little.

**Share ReFS blocks** requires the same supported ReFS volume, independent equal files, compatible integrity settings, non-sparse/uncompressed storage and whole-cluster ranges. Both paths remain and future writes remain independent. The host byte-compares source and target under stable handles, shares at most 64 MiB per native request, and verifies the target digest afterward. An unaligned trailing range stays in its original storage. Logical shared range bytes are reported separately from unknown physical reclaim. There is no filesystem migration or NTFS hardlink fallback.

Storage actions are limited to 1 GiB per file. Compression is one synchronous native operation; cancellation stops subsequent work and waits for the current operation and its final content check. ReFS cancellation can leave completed ranges shared, retaining identical payloads. Failures and partial changes mark the displayed scan stale. Compare/inspect again before another action. The host waits for outstanding work at shutdown and records storage mutations in its local activity log.

Native behavior follows Microsoft's [compression control](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_set_compression), [block cloning restrictions](https://learn.microsoft.com/en-us/windows/win32/fileio/block-cloning) and [sharing contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew). ReFS execution requires an actual supported volume; NTFS tests and successful packaging do not establish ReFS runtime proof.
