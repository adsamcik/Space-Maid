# Space Maid

A .NET 10 Windows desktop app for finding development clutter and reviewing potential cleanup. The WPF interface uses the built-in Fluent theme and follows Windows light/dark settings.

**Development cleanup is enabled.** Select findings and choose **Review cleanup** to check live folders and review exact paths, candidate allocation and cautions. **Keep folders** is the default; **Move to Recycle Bin** confirms the batch. Photos cleanup remains disabled in its first workflow.

The approved [extensions and Photos architecture](docs/extensions-and-photos-design.md) is implemented as a trusted local extension host, a separate read-only scan helper, and a bundled Photos workflow.

**Local assistant** is available through **Extensions → Local assistant → Open workflow**. Enable it, choose a compatible local GGUF instruction model and a scanned folder, then request investigation suggestions. It uses Microsoft.Extensions.AI with a separate Windows-isolated CPU worker and bounded access to deterministic scan summaries. Model text cannot authorize cleanup: selected suggestions require the host's live checks and separate user confirmation. See [setup and trust boundaries](docs/local-assistant.md).

## Run

Install the .NET 10 SDK, then run from this directory:

```powershell
dotnet run --project src/SpaceMaid.App -c Release
```

At startup, choose **Enable fast scanning** to authorize the bundled read-only helper through Windows UAC, or **Continue without admin**. Space Maid and extensions stay unelevated; cancelling UAC keeps standard scanning available. Choose a drive and click **Scan drive**. One helper is reused for the app session, including after scan cancellation and native scan failures. It exits when the app closes or disconnects. Cancellation is checked between metadata batches and during analysis. A broken connection falls back to standard scanning; **Enable fast scanning** starts a replacement. If Space Maid was manually launched as administrator, Photos and extensions remain unavailable until reopened normally.

## CI and license

[CI](.github/workflows/ci.yml) runs for pull requests, pushes to `main`, and manual dispatch. Linux builds the app and test bundle and publishes a Windows x64 package using the SDK pinned in `global.json`. A Windows job runs the Linux-built test bundle as a normal user, including the WPF and native filesystem checks. Test results, workflow timings and desktop renders are retained even after a test failure. No release or deployment is performed.

## Apps

**Apps** quickly finds installation folders on the selected drive using Windows' 32/64-bit installation records and shallow listings of common program, user-program and game folders. The sortable list starts with the largest folders and shows size bars, publishers, exact paths and searchable names. **Add app folder** includes a custom or portable installation; **Open folder** reveals the selected location. Returning to Apps retains its search, sort and selection.

Initial discovery reuses available drive-scan folder sizes where safe, then measures missing sizes in the background. **Refresh** re-discovers apps and measures current folder metadata. Measurement reads attributes and DATA-stream sizes, including named streams where supported, without opening app contents or running executables. Cancellation retains discovered rows and finished measurements. **On disk**, **File size**, **Installer estimate**, partial and unavailable results remain distinct; unknown size is never shown as zero. Shared install folders are grouped; overlapping folders and external hard links are disclosed rather than added into a misleading total.

These are installation-folder sizes. App data and caches elsewhere are excluded, and Windows Store packages or installations outside known locations may need **Add app folder**. Records without a usable install location cannot be assigned to a drive; inaccessible, linked and offline locations remain unmeasured. Discovery details show these gaps. Installation hints follow the [documented Windows uninstall registry fields](https://learn.microsoft.com/en-us/windows/win32/msi/uninstall-registry-key); installer-reported size is an estimate.

**Extensions** enables or disables packages after restart and adds explicitly trusted local directories containing `extension.json`, the entry DLL, its `.deps.json` and dependencies. Each package uses its own dependency load context while sharing WPF, Contracts and Core. Additional workflow views open from Extensions. Eligible provider-managed files and folders also offer **Make online-only**, including file rows and map blocks. Availability is checked asynchronously through Windows Cloud Files metadata; ordinary backup folders or provider names do not establish eligibility. The confirmation shows the exact path, provider, eligible file count, local data size and skipped-location reasons; **Keep offline** is the default. Live sync state and physical identity are checked again before each request. Unsynced, modified, excluded, local-only and already online-only files are skipped; linked paths are not followed. Windows receives an UNPINNED request for each eligible file, with bounded progress and cancellation. Accepted requests are reported separately from files observed to have released all local data. The sync app may complete requests later; no immediate saving is promised, and cancelled requests already accepted remain active. The app does not force dehydration, read file contents or change sync state.

This supports sync apps and modes that expose Windows' standard Cloud Files capability. It does not guarantee every version or mode of OneDrive/SharePoint, Proton Drive, Dropbox, Google Drive or other providers. Provider-specific/nonstandard integrations are not implemented. An ordinary folder being backed up cannot be made online-only through this menu.

Press **Delete** while Explore has focus to recycle its **selected folder**. One confirmation shows the exact path, observed sizes, and relevant cautions; **Keep folder** is the default. This includes the folder's current contents, even if the scan missed files or contents changed. Windows handles the Recycle Bin, progress, and cancellation on a separate STA thread so the app stays responsive. Cancellation can leave some contents already moved. Folder recycling has no permanent-delete fallback: a Windows callback requesting permanent deletion is refused. Drive roots, filesystem metadata, grouped or unresolved selections, files, reparse paths, and folders whose identity changed are blocked. If Windows cannot verify an identity, recycling is blocked. Delete in a path text field does not recycle folders, and Shift+Delete does not enable permanent deletion.

After recycling or online-only actions, metadata rechecks update the affected folders and parents, plus the Recycle Bin when it is inside the scanned scope. **Recheck this folder** refreshes its subtree, and a folder opened through the app in Explorer is rechecked when you return (deferred until idle if another operation is running). Changed metadata is merged into the existing inventory, retaining observed hard-link attribution, sorting, expansion, selection and unrelated branches; ancestor totals, opportunities, estimates and current drive free space are updated together. Other locations retain their original scan data. Cancelled, incomplete or unreconcilable refreshes stay **Out of date**, with global estimates and further manual file operations disabled until the affected scopes are successfully rechecked or a new scan completes. Opportunity selection and cleanup remain available after fresh validation of the selected folders. Refreshing an unrelated folder cannot clear that warning. There is no global watcher or polling for later provider completion; use a folder recheck to observe queued online-only results. Space moved to the Recycle Bin stays occupied until it is emptied. The separate **Empty…** action under Opportunities permanently deletes recycled items on the current drive.

Native recycling is recursive. Completion now requires Windows' selected-root callback, the confirmed native folder identity at its exact same-volume Recycle Bin destination, and an absent original path. **Check worktrees** explicitly runs a cancellable local inspection, separate from fast metadata scanning. The worktree controls offer **Old and already in upstream** (the default), **Old worktrees**, and **Already in upstream · any age**. The age slider covers **1–365 days**, starting at 30. Changing either control immediately updates matching counts and sizes from cached checks, without more Git commands or automatically selecting additional targets. **Select matching worktrees** adds the matching checkouts to the selection, ready for **Review cleanup**, without scrolling through the checklist. The activity threshold uses the latest observed file/folder modification (including ignored files) or HEAD/branch reflog activity; it does not measure last access or actual use. Missing activity evidence excludes age-based matches but does not prevent a verified upstream-only match. Age-only cleanup may include unmerged commits; their branches and shared Git storage are retained.

Every rule requires a registered, unlocked linked worktree on a branch with verified clean tracked/untracked state. Upstream rules require HEAD contained in its configured upstream or one cached remote default. Cached refs may be out of date; nothing is fetched, no branch is deleted, and Git status may read ordinary local contents. Submodules/nested repositories, special index flags, unsafe Git configuration, cloud/provider/reparse storage, missing required evidence, oversized inspections and timeouts remain **Other worktrees**, with reasons and last observed activity in folder details and local logs. Each checkout has a 10-second budget and bounded metadata/output, with at most 4,096 paths held stable during Git reads. Repositories using per-worktree configuration need manual review. This is a live inspection: new entries introduced by external software can reach Git before final validation, so concurrent provider changes cannot carry an absolute no-hydration guarantee. Each UI run stops after two minutes, retaining completed results so **Check remaining worktrees** can continue.

Selected worktree opportunities, including those selected individually, are checked against their captured cleanup rule and fresh folder metadata before review and before each recycle. Changed or uncertain targets are skipped, and selected ancestors containing shared Git storage are blocked. Changing a rule unchecks selected worktrees that no longer match; retained selections adopt the displayed rule. Once review starts, its captured rule is immutable. Recycling retains branches and Git registration so restoring the checkout remains possible; it does not prune Git metadata. Snapshot refreshes invalidate displayed Git assessments, while retained selections keep their captured fresh-check requirement.

**Review cleanup** checks the selected subtrees and their immediate parents before every review, even when the inventory has no known stale flag. The parent check refreshes classification evidence such as project manifests without recursively scanning unrelated siblings. Missing folders, replaced native directory identities and locations that no longer match their original rule are excluded and unchecked; newly discovered locations are never automatically selected. Native results update the shared inventory while preserving scope, filters and unrelated stale warnings. Newly observed sibling folders with unscanned contents show **Not checked**, with partial ancestor totals, until their own recheck completes. Logical-only scans get a fresh selection-only estimate with physical savings unknown; the full inventory remains explicitly out of date. Review shows when the locations were checked and how many were excluded. Cancellation, access failures or incomplete metadata leave the previous results marked out of date and do not open an unvalidated review. Cancellation after coherent publication retains the completed inventory update but still prevents the review from opening. Large selected folders can still take time to enumerate; checks are cancellable, metadata-only observations rather than an atomic filesystem snapshot.

The cleanup review lists eligible and blocked folders with their exact paths and cautions. Nested selections are covered once by their selected ancestor. Confirmation starts a serial, cancellable Recycle Bin batch, with another metadata/rule check and the pre-confirmation physical identity retained through the recycler's final Windows callback. Missing, replaced, protected and unsupported targets are skipped; failures are reported per location and other eligible folders can continue. Progress shows the current folder and completed count; Windows provides progress/cancellation for each folder. Closing during execution cancels and waits for the owned operation to finish. Results remain visible, and another attempt requires a new review. Folder cleanup has no permanent-delete fallback; emptying the bin is a separate action.

Cleanup includes the confirmed folders' current contents, including custom files. Stop active tools and preserve work first. A linked checkout's `.git` pointer does not prove clean or merged work, and recycling does not deregister worktrees/submodules through Git. Deleting synced folders can also delete cloud copies or propagate to other devices; use **Make online-only** when the intent is only to release local storage. After native-identity cleanup, affected parents, surviving subtrees and in-scope Recycle Bin locations are rechecked and published together. Cancelled/failed refreshes retain an explicit out-of-date state. Logical-only cleanup captures live native identities when available but cannot merge its sparse validation into the old full inventory; it updates drive space and requires a rescan of that inventory. Unsupported live identity blocks cleanup.

Grouping uses existing `.git` and project-manifest filename metadata, without Git commands or content reads. A linked checkout beneath a detected Git folder stays with that containing project; external linked checkouts retain their own folder groups. These are folder contexts, not proof of common Git repository identity, inactivity, a clean checkout or integrated branches. Group sizes cover the full group even when filtered, collapse nested findings within each group, and represent observed allocation rather than guaranteed savings. Different clutter-type groups can overlap. Cautions, **Show in tree**, and cleanup review remain available.

The actual backend and any fallback reason appear live below the scan status. **Open log** is available during scanning and after completion, cancellation, or failure. Each scan writes timestamped JSONL diagnostics under `%LOCALAPPDATA%\SpaceMaid\Logs`: executable/build/admin state, backend attempts and Windows errors, query/batch/object/name counts, overall object rate, native-query/parsing time, memory, coverage warnings, analysis/explorer timings, and the final outcome. There is no file-content or per-file tracing. Progress samples are written at most once per second; state changes and warnings are recorded when they occur. Logs are capped at 10 MB with an explicit limit marker, and the newest 10 are retained (an older log still open by another scan may survive until a later rotation). Logging failures are shown without stopping scanning. Logs can contain the target and skipped paths, and stay local.

**Scan details** shows the actual backend and fallback reason, files/folders/names, metadata throughput, phase timings, process peak memory, managed allocation traffic, accounting limits, and bounded coverage diagnostics. Process peak is a lifetime high-water mark, allocation traffic is not retained memory, and explorer preparation time does not include completed UI rendering.

## What it finds

- .NET `bin`/`obj` beside a project file; Node dependencies and possible build output beside `package.json`.
- Python environments identified by `pyvenv.cfg`, and bytecode caches containing `.pyc` files.
- Standard NuGet, npm, pip, and Gradle cache locations.
- Codex logs/session history, Claude Code debug files, and linked Git checkouts identified by a `.git` pointer file.

Findings are evidence for review, not proof that every file is disposable. Linked checkouts can be worktrees or submodules. Initial detection does not audit their source changes or untracked files; explicit worktree checks do. Age never establishes abandonment. Custom cache locations and other agent/tool storage layouts are not automatically recognized in this first release. Detection uses metadata, not file-content inspection.

## Scanner and accounting

Eligible whole local NTFS volumes use Windows' documented [`FSCTL_QUERY_FILE_LAYOUT`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/fsctl-query-file-layout) with names, data streams (including streams without clusters), and extra metadata. Acquisition is serial, with a reusable pooled buffer and bounds-checked relative-offset parsing. Unsupported access or layout data falls back to buffered directory enumeration.

The standard backend uses `FileIdExtdDirectoryInfo`, retaining 128-bit identities, logical sizes, and reported allocation. Providers that do not expose usable identities fall back to basic enumeration, with logical-size-only and hard-link limitations disclosed. Standard scanning does not fully enumerate alternate data streams. Junction/symbolic-link targets are not followed; inaccessible locations produce coverage warnings. No content is read to hash duplicates or hydrate cloud files. A provider can still do its own work in response to metadata queries.

Rechecks use native directory metadata for the requested scopes. A fast-scan inventory also requires attribute-only `FileStreamInfo` queries there, preserving named/resident/sparse DATA-stream size accounting; failure leaves the previous results out of date. Directory enumeration cannot reread the hidden reserved NTFS namespace, so positively identified reserved entries and their cached descendants retain their original scan data, explicitly disclosed in Scan details. A refresh no longer claims complete volume-wide hard-link coverage, since names added elsewhere have not been reread. Disk access is scoped, but merging, aggregation and opportunity analysis rebuild the in-memory inventory off the UI thread; large inventories can still incur CPU and memory cost. Rechecks are observations, not an atomic filesystem snapshot.

File objects and name links are separate compact records; basenames share a character arena. Full paths are constructed only when needed. Parent resolution and bottom-up aggregation avoid repeatedly walking ancestors. Expanded tree branches retain compact indexes; visible display rows and recycled UI containers are created on demand. Folder sorting and map aggregation run off the UI thread and reuse the scan inventory. Scan inventories remain in memory; diagnostics are stored locally. There is no persistent file index, journal creation, service, telemetry, or network upload.

Observed allocation is attributed once per file object. Candidate plans collapse nested selections and exclude allocation with observed names outside the selection. External hard links, incomplete scans, cloud/provider storage, and changes after scanning can reduce actual savings. Resident data and filesystem metadata can also prevent reported per-file allocation from becoming freed volume clusters. Logical size, observed allocation, drive usage, and reclaimable space are different quantities. Estimates are never a promise of space freed.
