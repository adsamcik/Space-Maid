# Space Maid

A .NET 10 Windows desktop app for finding development clutter and reviewing potential cleanup. The WPF interface uses the built-in Fluent theme and follows Windows light/dark settings.

**Bulk cleanup is preview only.** Select findings and choose **Review selection** to see exact paths, estimated candidate space, and cautions. **Clean up** is disabled and the core rejects execution of those plans. Manual folder recycling in Explore is available with a separate confirmation.

The approved [extensions and Photos architecture](docs/extensions-and-photos-design.md) is implemented as a trusted local extension host, a separate read-only scan helper, and a bundled Photos workflow.

## Run

Install the .NET 10 SDK, then run from this directory:

```powershell
dotnet run --project src/SpaceMaid.App -c Release
```

At startup, choose **Enable fast scanning** to authorize the bundled read-only helper through Windows UAC, or **Continue without admin**. Space Maid and extensions stay unelevated; cancelling UAC keeps standard scanning available. Choose a drive and click **Scan drive**. Cancellation is checked between metadata batches and during analysis. A helper handles one local NTFS scan and exits; further fast scans request a new helper. If Space Maid was manually launched as administrator, Photos and extensions remain unavailable until reopened normally.

## Photos and extensions

**Photos** has collections, a sortable file list with 100 rows per page, and selection details. **Add folder** and **Refresh** discover current metadata without reading media contents. **Analyze** explicitly enables read-only ExifTool inspection, comparison of complete default streams, and lazy previews for that collection. Paging and selection remain available during analysis; discovery shows bounded preliminary pages. Refresh invalidates earlier content authorization, including when interrupted. An incomplete refresh retains unseen locations instead of declaring them deleted.

**Duplicates** compares SHA-256 hashes of stable full default streams from distinct physical files. Hard-link aliases are shown without being treated as additional copies. Equal image bytes do not establish equality of alternate streams, sidecars or edits. **Families** shows possible RAW/JPEG/XMP/ACR relationships within the same folder; filenames alone do not establish equivalent images. Selection shows exact related paths and permits a retained-copy review preference. Photo cleanup and conversion stay disabled.

Previews use installed Windows codecs, fit within 160 pixels, and disclose missing codecs. Recognized Windows Cloud Files placeholders, reparse and offline files stay metadata-only, including fully local placeholders whose ordinary attributes hide their provider state. The app does not hydrate them. RAW previews may differ from current edits. Scoped metadata discovery cannot establish complete external hard-link coverage or all-stream allocation; unknown allocation and potential recovery stay explicit.

The host admits at most 128 jobs, with one content-analysis worker and two thumbnail workers. Foreground discovery pauses content work between checkpoints. Photos retains at most 64 MiB in its decoded cache and 512 MiB in its evictable disk cache; these are cache limits, not a whole-process memory guarantee. Its SQLite catalog, interruption records and cache live in `%LOCALAPPDATA%\SpaceMaid\Extensions\space-maid.photos`. Catalog reads and writes run off the UI thread. The pinned dependencies are `Microsoft.Data.Sqlite` 10.0.10 and `SQLitePCLRaw.bundle_e_sqlite3` 2.1.13.

**Extensions** enables or disables packages after restart and adds explicitly trusted local directories containing `extension.json`, the entry DLL, its `.deps.json` and dependencies. API version 1 is defined in `SpaceMaid.Extensions.Contracts`; extensions reference that contract rather than App/Core. Each package uses its own dependency load context while sharing WPF and the contract. Additional workflow views open from Extensions. This is dependency isolation, not a security sandbox: trusted extensions execute local code with your account's permissions. Disabled packages execute no extension code and keep their catalogs.

The host's ExifTool adapter uses the existing executable at `%LOCALAPPDATA%\Programs\ExifTool\ExifTool.exe`, numbered persistent read-only requests, bounded replies and timeouts. It validates and holds inputs before launching the tool; cancellation/shutdown stops only its owned process. Missing ExifTool leaves richer metadata unavailable while stable byte comparison can still run. It installs no tools and invokes no Adobe software.

While scanning, **Explore space** shows **Preliminary** allocated/logical totals and up to 100 largest regular file objects found so far, refreshed about once a second between metadata batches. It ranks allocation when available, otherwise logical size, and counts shared file objects once when identities are available. Basic logical-only mode discloses that hard links may repeat. Exact paths appear as parent records become available; unresolved paths are explicitly marked pending. These are partial observed sizes, not folder totals or cleanup estimates. Cancellation retains the latest bounded preview; a backend fallback clears it before the new acquisition. The full tree, treemap, and cleanup estimates replace the preview when ready. Updates do not repeatedly copy or aggregate the full inventory, and benchmarks without a progress subscriber do not maintain the preview index.

**Explore space** shows the full observed folder/file tree, sorted largest first, with allocated size, logical size, and share of the parent. Expand folders with their arrows or the keyboard's Left/Right keys. Selecting a row updates the treemap; selecting a map block drills into that location. Breadcrumbs navigate back up. Shared hard-link names stay visible, but their allocation is attributed once; additional names contribute zero extra allocation. Known incomplete branches are marked **Partial**.

Drive controls, Free/Scanned/Candidate summaries, and a free-capacity bar share a compact two-row header. Click a tree or preliminary-list column heading to sort: names start A–Z, numbers start largest first, and repeated clicks reverse the order with an arrow. Tree sorting changes siblings within each folder and preserves expansion and selection; the map remains ordered by contribution size.

File selection details and tree, map, and preliminary-file tooltips show an **Inferred type** from the filename extension: images, RAW photos, video, audio, source/configuration, documents, archives/installers, binaries, databases, disk images, and logs/temporary files. Unrecognized suffixes show **Unknown**; names without a suffix show **No extension**. Matching is case-insensitive and uses the final suffix (for example, `.tar.gz` uses `.gz`). This runs only for displayed files using existing metadata, with no content reads or new dependencies. A name is a hint, not format validation or permission to delete. Clutter colors and cleanup rules are independent of file type.

Right-click a resolved folder in the tree or treemap for **Open in File Explorer**, **Move to Recycle Bin**, and **Recheck this folder**. Right-click selects the entry and updates its details without drilling into the folder. Menu actions retain the location on which the menu was opened; later selection or a different scan cannot redirect them. The keyboard context-menu key or Shift+F10 opens operations for the selected tree entry. Recycling is disabled for protected entries and outdated scans, and still uses the same live validation and confirmation. Grouped map entries, unresolved entries, and blank areas do not expose operations.

Eligible provider-managed files and folders also offer **Make online-only**, including file rows and map blocks. Availability is checked asynchronously through Windows Cloud Files metadata; ordinary backup folders or provider names do not establish eligibility. The confirmation shows the exact path, provider, eligible file count, local data size and skipped-location reasons; **Keep offline** is the default. Live sync state and physical identity are checked again before each request. Unsynced, modified, excluded, local-only and already online-only files are skipped; linked paths are not followed. Windows receives an UNPINNED request for each eligible file, with bounded progress and cancellation. Accepted requests are reported separately from files observed to have released all local data. The sync app may complete requests later; no immediate saving is promised, and cancelled requests already accepted remain active. The app does not force dehydration, read file contents or change sync state.

This supports sync apps and modes that expose Windows' standard Cloud Files capability. It does not guarantee every version or mode of OneDrive/SharePoint, Proton Drive, Dropbox, Google Drive or other providers. Provider-specific/nonstandard integrations are not implemented. An ordinary folder being backed up cannot be made online-only through this menu.

Press **Delete** while Explore has focus to recycle its **selected folder**. One confirmation shows the exact path, observed sizes, and relevant cautions; **Keep folder** is the default. This includes the folder's current contents, even if the scan missed files or contents changed. Windows handles the Recycle Bin, progress, and cancellation on a separate STA thread so the app stays responsive. Cancellation can leave some contents already moved. There is no permanent-delete action: a Windows callback requesting permanent deletion is refused. Drive roots, filesystem metadata, grouped or unresolved selections, files, reparse paths, and folders whose identity changed are blocked. If Windows cannot verify an identity, recycling is blocked. Delete in a path text field does not recycle folders, and Shift+Delete does not enable permanent deletion.

After recycling or online-only actions, metadata rechecks update the affected folders and parents, plus the Recycle Bin when it is inside the scanned scope. **Recheck this folder** refreshes its subtree, and a folder opened through the app in Explorer is rechecked when you return (deferred until idle if another operation is running). Changed metadata is merged into the existing inventory, retaining observed hard-link attribution, sorting, expansion, selection and unrelated branches; ancestor totals, opportunities, estimates and current drive free space are updated together. Other locations retain their original scan data. Cancelled, incomplete or unreconcilable refreshes stay **Out of date**, with global estimates and further manual file operations disabled until the affected scopes are successfully rechecked or a new scan completes. Opportunity selection and validated read-only review remain available. Refreshing an unrelated folder cannot clear that warning. There is no global watcher or polling for later provider completion; use a folder recheck to observe queued online-only results. Space moved to the Recycle Bin stays occupied until it is emptied; the app does not empty it.

The treemap uses allocation when available and explicitly switches to logical size otherwise. It fills the available pane below one breadcrumb/size row and shows a compact selected-path/size strip. Folders contributing at least 25% can show one nested child level, with at most 64 blocks across both levels. Framed parent folders have a separate title/size band, outlined child tiles, wider gutters and alternating sibling shades. Narrow parent bands stack the size below the name. Grouped entries use dashed outlines; every observed name remains available in the tree. Parent headers and nested folders retain navigation and folder operations. Details that do not fit remain available in tooltips and the tree. Map colors reflect the existing detection rules and do not establish that files are disposable.

**Opportunities** starts with the largest project/folder group. Its navigator shows observed candidate size, location counts and selected counts. Switch **Group by** to clutter type, sort by size/name/count, or choose **All locations**. Search matches titles, full paths, types and project names; a type filter narrows the results further. Scoped lists show relative paths under the full group location, while exact paths remain in tooltips and selection details. **Select listed** selects only the current group/filter results for read-only review; **Clear selection** clears all checked locations. Selections survive navigation, filters and targeted refresh, and the footer reports selected locations outside the current view. Out-of-date findings keep their group context with a separate warning, and remain selectable.

**Review selection** checks the selected subtrees and their immediate parents before every preview, even when the inventory has no known stale flag. The parent check refreshes classification evidence such as project manifests without recursively scanning unrelated siblings. Missing folders, replaced native directory identities and locations that no longer match their original rule are excluded and unchecked; newly discovered locations are never automatically selected. Native results update the shared inventory while preserving scope, filters and unrelated stale warnings. Newly observed sibling folders with unscanned contents show **Not checked**, with partial ancestor totals, until their own recheck completes. Logical-only scans get a fresh selection-only preview with physical savings unknown; the full inventory remains explicitly out of date. Review shows when the locations were checked and how many were excluded. Cancellation, access failures or incomplete metadata leave the previous results marked out of date and do not open an unvalidated preview. Cancellation after coherent publication retains the completed inventory update but still prevents the preview from opening. Large selected folders can still take time to enumerate; checks are cancellable, metadata-only observations rather than an atomic filesystem snapshot. Bulk cleanup remains disabled.

Grouping uses existing `.git` and project-manifest filename metadata, without Git commands or content reads. A linked checkout beneath a detected Git folder stays with that containing project; external linked checkouts retain their own folder groups. These are folder contexts, not proof of common Git repository identity, inactivity, a clean checkout or integrated branches. Group sizes cover the full group even when filtered, collapse nested findings within each group, and represent observed allocation rather than guaranteed savings. Different clutter-type groups can overlap. Cautions, **Show in tree**, and the disabled bulk-cleanup review remain available.

The actual backend and any fallback reason appear live below the scan status. **Open log** is available during scanning and after completion, cancellation, or failure. Each scan writes timestamped JSONL diagnostics under `%LOCALAPPDATA%\SpaceMaid\Logs`: executable/build/admin state, backend attempts and Windows errors, query/batch/object/name counts, overall object rate, native-query/parsing time, memory, coverage warnings, analysis/explorer timings, and the final outcome. There is no file-content or per-file tracing. Progress samples are written at most once per second; state changes and warnings are recorded when they occur. Logs are capped at 10 MB with an explicit limit marker, and the newest 10 are retained (an older log still open by another scan may survive until a later rotation). Logging failures are shown without stopping scanning. Logs can contain the target and skipped paths, and stay local.

**Scan details** shows the actual backend and fallback reason, files/folders/names, metadata throughput, phase timings, process peak memory, managed allocation traffic, accounting limits, and bounded coverage diagnostics. Process peak is a lifetime high-water mark, allocation traffic is not retained memory, and explorer preparation time does not include completed UI rendering.

src/SpaceMaid.App/bin/Release/net10.0-windows/SpaceMaid.App.exe

## What it finds

- .NET `bin`/`obj` beside a project file; Node dependencies and possible build output beside `package.json`.
- Python environments identified by `pyvenv.cfg`, and bytecode caches containing `.pyc` files.
- Standard NuGet, npm, pip, and Gradle cache locations.
- Codex logs/session history, Claude Code debug files, and linked Git checkouts identified by a `.git` pointer file.

Findings are evidence for review, not proof that every file is disposable. Linked checkouts can be worktrees or submodules. Their source changes and untracked files are not audited, and age never establishes abandonment. Custom cache locations and other agent/tool storage layouts are not automatically recognized in this first release. Detection uses metadata, not file-content inspection.

## Scanner and accounting

Eligible whole local NTFS volumes use Windows' documented [`FSCTL_QUERY_FILE_LAYOUT`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/fsctl-query-file-layout) with names, data streams (including streams without clusters), and extra metadata. Acquisition is serial, with a reusable pooled buffer and bounds-checked relative-offset parsing. Unsupported access or layout data falls back to buffered directory enumeration.

The standard backend uses `FileIdExtdDirectoryInfo`, retaining 128-bit identities, logical sizes, and reported allocation. Providers that do not expose usable identities fall back to basic enumeration, with logical-size-only and hard-link limitations disclosed. Standard scanning does not fully enumerate alternate data streams. Junction/symbolic-link targets are not followed; inaccessible locations produce coverage warnings. No content is read to hash duplicates or hydrate cloud files. A provider can still do its own work in response to metadata queries.

Rechecks use native directory metadata for the requested scopes. A fast-scan inventory also requires attribute-only `FileStreamInfo` queries there, preserving named/resident/sparse DATA-stream size accounting; failure leaves the previous results out of date. Directory enumeration cannot reread the hidden reserved NTFS namespace, so positively identified reserved entries and their cached descendants retain their original scan data, explicitly disclosed in Scan details. A refresh no longer claims complete volume-wide hard-link coverage, since names added elsewhere have not been reread. Disk access is scoped, but merging, aggregation and opportunity analysis rebuild the in-memory inventory off the UI thread; large inventories can still incur CPU and memory cost. Rechecks are observations, not an atomic filesystem snapshot.

File objects and name links are separate compact records; basenames share a character arena. Full paths are constructed only when needed. Parent resolution and bottom-up aggregation avoid repeatedly walking ancestors. Expanded tree branches retain compact indexes; visible display rows and recycled UI containers are created on demand. Folder sorting and map aggregation run off the UI thread and reuse the scan inventory. Scan inventories remain in memory; diagnostics are stored locally. There is no persistent file index, journal creation, service, telemetry, or network upload.

Observed allocation is attributed once per file object. Candidate plans collapse nested selections and exclude allocation with observed names outside the selection. External hard links, incomplete scans, cloud/provider storage, and changes after scanning can reduce actual savings. Resident data and filesystem metadata can also prevent reported per-file allocation from becoming freed volume clusters. Logical size, observed allocation, drive usage, and reclaimable space are different quantities. Estimates are never a promise of space freed.

## Check and measure

```powershell
dotnet build SpaceMaid.slnx -c Release -m:1
dotnet test tests/SpaceMaid.Tests -c Release -m:1
dotnet run --project tools/SpaceMaid.Bench -c Release -- 'G:\Github\Space-Maid' --standard
# From an administrator terminal, benchmark a whole NTFS volume:
dotnet run --project tools/SpaceMaid.Bench -c Release -- 'G:\'
# Add the same bounded diagnostic logs to a benchmark:
dotnet run --project tools/SpaceMaid.Bench -c Release -- 'G:\' --log-directory 'artifacts\benchmark-logs'
```

The benchmark prints the actual backend, metadata/aggregation elapsed time, allocation traffic, peak working set, coverage flags, and warnings. Compare equally complete work and distinguish warm from cold scans. A small folder scan does not establish whole-drive speed or parity with WizTree.

On 10 October 2026, one standard metadata scan of `G:\Github` returned 3,898,239 file objects and 3,932,055 names in 174.44 seconds: 174.12 seconds acquisition and 0.314 seconds aggregation. Peak working set was 1.31 GiB; managed allocation traffic was 2.61 GiB (not retained memory). It reported 100 coverage warnings, including un-followed junction/link targets. Cache state was uncontrolled. This measures the folder fallback only, excludes complete alternate-stream/external-link coverage, and does not time detection or UI presentation. It establishes neither whole-volume nor bulk NTFS speed.

After correcting the NTFS control code and version-1 unnamed DATA stream recognition, an elevated whole-volume `G:\` scan on 10 October 2026 used **Fast NTFS scan** without fallback: 4,193,946 objects, 4,228,719 names, 42.25 seconds total (41.22 seconds acquisition, 0.981 seconds aggregation), 480,182,886,432 allocated bytes, and no coverage warnings. The log measured 37.45 seconds inside metadata queries, 3.072 seconds parsing, and 1,712 parsed batches. Peak working set was 2.26 GB; managed allocation traffic was 2.55 GB. Cache state was uncontrolled; concurrent activity can affect results. This excludes detection and UI presentation, and is not an equal-scope comparison with the earlier folder scan or a measured WizTree comparison. Windows query time dominates this run; a direct MFT backend would be a separate architecture change.
